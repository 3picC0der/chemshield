# ChemShield Model A design and experiment plan

## 1. Design decision

Model A is a pre-actuation context gate. It decides whether an authenticated,
fresh, structurally valid, statically bounded dose is contextually acceptable
for the current process state.

It does not infer malicious intent. The operational labels are:

- `ACCEPTABLE_CONTEXT`
- `HARMFUL_CONTEXT`
- `UNCERTAIN_CONTEXT`

An injected attack family is stored as scenario metadata, not used as the
training target. This allows the same unsafe behavior to represent an attack,
operator mistake, configuration error, or stale plan without changing the
safety decision.

Model A can block a request. It cannot authorize a request by itself and cannot
override authentication, chemistry limits, PLC interlocks, or the emergency
stop.

## 2. Position in the execution path

The recommended order is:

1. Validate schema, finite values, session, role, authentication, freshness,
   nonce, sequence number, action hash, configuration version and static dose
   bounds.
2. Validate sensor age, heartbeat, interlocks and controller state.
3. Calculate the nominal chemical effect and apply hard chemistry limits.
4. Build the frozen Model A feature vector from only information available
   before actuation.
5. Run Model A.
6. Allow the PLC to evaluate its local interlocks only when all previous gates
   pass.

Any invalid input, inference exception, timeout, unsupported feature range or
uncertain decision fails closed.

## 3. Required output contract

For every evaluated command, store:

- `command_id`, `event_id`, `plan_id` and timestamp;
- model name, version and artifact checksum;
- feature-schema version and feature-quality flags;
- `p_harmful_context`;
- `ACCEPT`, `BLOCK` or `UNCERTAIN`;
- threshold and reason codes;
- feature extraction, inference and total decision latency;
- independent gateway, physics-rule and PLC verdicts; and
- final actuation result.

The probability must be calibrated before it is presented as a probability.
Until calibration is validated, call it a risk score.

## 4. Learning target

The first model should be binary:

`y = 1` when executing the exact candidate under the ground-truth scenario
would produce a contextually harmful result; otherwise `y = 0`.

The prototype label considers a request harmful when it would:

- move the true pH beyond the 5.5--9.5 extreme-safety interval;
- move an already abnormal process materially farther away from neutral; or
- overshoot from one side of the recovery interval to the other.

The final team-approved label must be generated by a versioned policy function,
not manually improvised for individual samples. Deterministic violations such
as stale data, lost heartbeat or more than 50 mmol per event remain rule labels
and should normally be removed before the learning dataset is built.

## 5. Initial feature contract

The starting feature set uses summary features rather than a neural sequence
model:

| Feature | Meaning | Source |
| --- | --- | --- |
| `ph_mean_5s` | Mean of genuine recent pH samples | pH acquisition |
| `ph_slope_5s` | Linear pH trend | pH acquisition |
| `ph_curvature_5s` | Change in slope | pH acquisition |
| `ph_std_5s` | Short-window variability | pH acquisition |
| `sample_age_s` | Age of newest genuine sample | acquisition service |
| `candidate_direction` | Acid `+1`, base `-1` | exact command |
| `candidate_mmol` | Requested amount of active reagent | exact command |
| `predicted_post_ph` | Nominal CHE prediction | chemistry estimator |
| `predicted_safety_margin` | Distance to the nearest 5.5/9.5 limit | estimator |
| `cumulative_signed_mmol` | Net requested reagent in the current event | audit log |
| `cumulative_abs_mmol` | Total requested reagent in the current event | audit log |
| `request_delivery_residual` | Previous delivered/requested estimate | dosing audit |
| `measured_predicted_residual` | Previous pH response residual | estimator/audit |
| `mixer_speed_ratio` | Actual/target mixer speed | mixer feedback |
| `level_margin_l` | Estimated liquid margin to level limit | level inputs |
| `heartbeat_age_s` | Controller heartbeat age | gateway/PLC |

Do not manufacture ten independent pH samples per second from a 1 Hz sensor.
Store the original timestamp and age. A future sequence model should consume
genuine samples and masks for missing values.

## 6. Dataset hierarchy

### Tier 0: equation-based generator

Use the FDR mole balance to verify interfaces, labels, grouping, metrics and
timing. Randomize volume, initial pH, sensor bias, measurement noise, pump gain,
mixing response and command history. This is the dataset produced by the
prototype.

Use it for software evidence only. It cannot establish physical accuracy.

### Tier 1: Aspen or a higher-fidelity dynamic simulator

Use a dynamic model to vary mixing delay, sensor lag, imperfect dosing,
temperature, volume, reagent concentration and disturbances. Export the same
signal schema as the Tier 0 generator. Keep simulator parameters and random
seeds in the scenario manifest.

Aspen Plus Dynamics is useful for transient and control scenarios, but the
model must first be parameterized for this bench process. More fidelity does
not compensate for incorrect parameters.

### Tier 2: public ICS datasets

Use HAI or SWaT to study time-series handling, anomaly metrics, missing values,
actuator/sensor temporal patterns and evaluation tooling. Do not map their tags
directly into ChemShield chemical labels and do not use them as the final test
set.

HAI is openly distributed and includes normal and attack data from a coupled
hardware-in-the-loop ICS testbed. SWaT is available from iTrust by request and
has its own terms of use. Neither reproduces the ChemShield vessel, reagent
concentrations or dose-response relation.

### Tier 3: hardware-in-the-loop and physical data

Collect normal commands first, then bounded fault and harmful-context cases.
Use temporary ground-truth instrumentation where possible:

- a balance or reference flow measurement for delivered volume;
- an independent calibrated pH reference;
- synchronized command, PLC, tachometer and sensor timestamps; and
- recorded calibration, concentration, volume and temperature.

Physical experiments are reserved for domain validation and final acceptance,
not for discovering basic software bugs.

## 7. Scenario matrix

Every dataset row belongs to an episode and a run. A scenario manifest should
record the following dimensions:

- starting pH, volume and temperature;
- acid/base channel, concentration and volume;
- distance to the operational and extreme-safety boundaries;
- recent same-direction and opposite-direction commands;
- normal, biased, noisy, delayed or stale sensor behavior;
- nominal, underdelivering and overdelivering pump behavior;
- normal and degraded mixing;
- command origin: normal, operator error, configuration error or injected
  context-aware attack; and
- generator/model/calibration versions.

The same dose must appear in both safe and harmful contexts. Otherwise the
model may learn that a particular volume is always dangerous rather than learn
the interaction between command and process state.

## 8. Data split and leakage controls

Split by complete physical or simulated run, never by individual rows. Keep all
candidate commands derived from the same trajectory in one split. Also create:

- an unseen initial-condition test;
- an unseen pump/sensor uncertainty test;
- an unseen command-pattern test; and
- eventually, a synthetic-train/physical-test evaluation.

Do not tune thresholds, features or hyperparameters on the final test set.

## 9. Model sequence

Train the following in order:

1. gateway-only baseline;
2. nominal chemistry-rule baseline;
3. logistic regression;
4. shallow decision tree;
5. random forest;
6. gradient-boosted trees; and
7. only after enough genuine sequential data, a compact temporal convolution
   or recurrent model.

A fine-tuned language model is not appropriate. A pretrained time-series model
is also unnecessary for the first prototype because the signals and safety
contract are small, structured and process-specific. The contribution comes
from context and validation, not model size.

Select the smallest model that meets the safety and latency targets. Calibrate
its score using a validation set that is disjoint from model fitting.

## 10. Evidence plan

### Existing FDR requirements

| Requirement | Model A evidence |
| --- | --- |
| C2: gateway is sole actuator path | Integration test proves every accepted dose has gateway, physics and Model A verdicts before PLC enable |
| C3: no more than 50 mmol/event | Deterministic cumulative-dose veto; confirm Model A cannot bypass it |
| S3: replay/stale rejection | Gateway evidence only; do not attribute this to Model A |
| S4: class and risk within 3 s | Benchmark feature extraction, inference and risk mapping on the Raspberry Pi |
| INT-S1: unsafe event to hold within 2 s | End-to-end harmful-request test from receipt to inhibited output; separate this from physical-disturbance detection |
| INT-S2: recovery within 300 s | Verify Model A latency does not consume the integration reserve; recovery performance belongs to CHE/ISE |
| INT-S3: avoid pH below 5.5 or above 9.5 | Counterfactual simulation comparing gateway-only, chemistry rules and rules plus Model A |

### Proposed AI acceptance requirements

Freeze the numerical targets with the team before final testing. Reasonable
design-stage targets are:

- zero missed hazardous commands in the defined acceptance suite, with the
  number of independent cases and a binomial confidence interval reported;
- benign false-block rate at or below 5% on the held-out test;
- feature extraction plus inference p99 below 100 ms on the Raspberry Pi and
  total class/risk decision below the existing 3 s requirement;
- 100% fail-closed behavior for invalid features, timeout, missing model and
  unsupported schema version; and
- reproducible audit output for every test case.

### Required comparisons

Run all systems on exactly the same held-out cases:

1. gateway only;
2. gateway plus static limits;
3. gateway plus nominal chemistry prediction;
4. Model A alone; and
5. gateway plus chemistry rules plus Model A.

The meaningful AI contribution is the additional harmful contexts caught at an
acceptable increase in benign blocks. If Model A does not improve the hybrid
system, report that result and redesign the features or narrow the AI claim.

## 11. Development stages

### Stage A: software proof

- Freeze the feature and output schemas.
- Run the Tier 0 simulator.
- Establish leakage-safe splits and baselines.
- Produce confusion matrices, threshold curves, latency distributions and
  example decisions for identical commands in different contexts.

Exit condition: the pipeline is reproducible and the hybrid comparison is
complete.

### Stage B: model and simulator refinement

- Add measured pump calibration, sensor lag/noise and mixing response.
- Add cumulative small-dose, near-boundary and model-mismatch scenarios.
- Compare logistic regression, random forest and boosted trees.
- Calibrate the selected risk score and freeze the threshold.

Exit condition: the selected model improves on the nominal-physics baseline on
unseen scenarios without exceeding the false-block limit.

### Stage C: integration simulation

- Replay signed commands through the real gateway interface.
- Include inference timeout, malformed features and stale model tests.
- Verify that a block produces no PLC enable and that every decision is logged.
- Measure total latency using the same clock used for the requirement.

Exit condition: C2, C3, S4 and the request-related part of INT-S1 have executable
evidence.

### Stage D: physical validation

- Begin in shadow mode, where the model logs decisions but cannot block.
- Collect independent normal runs and bounded harmful-context experiments.
- Evaluate the frozen model before retraining.
- Retrain only if the synthetic-to-physical gap is documented and a new final
  test set remains untouched.

Exit condition: the team can state precisely which claims are simulation-only
and which are supported by the physical prototype.
